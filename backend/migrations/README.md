# Миграции базы данных

Каталог содержит SQL-миграции двух типов: **bootstrap** (наполнение пустой БД)
и **one-off** (корректировки существующих БД). Применяются через Taskfile
(`task db:migrate`, `task db:migrate:bootstrap`).

## Структура каталога

```
migrations/
├── bootstrap/   # справочники для пустой/новой БД (новый сервер, перенос проекта)
└── one-off/     # разовые корректировки существующих БД (применяются на каждом деплое)
```

## Schema vs Data migrations vs Seeds

В проекте разделены три слоя работы с БД (см. [backend/AGENTS.md](../AGENTS.md)):

| Слой | Что делает | Когда применяется | Инструмент |
|---|---|---|---|
| **Schema migrations** | DDL: таблицы, индексы, колонки | При каждом старте приложения (auto-migrate) | Ent `client.Schema.Create` в `config.RunMigrations` |
| **Bootstrap-миграции (SQL)** | Наполнение пустой БД справочниками (`ref_locations`, `ref_breeds`) | Вручную, один раз — только при создании проекта или переносе на новый сервер | `task db:migrate:bootstrap` (psql) |
| **One-off миграции (SQL)** | Разовые преобразования уже существующих данных/индексов (бэкфиллы, дроп индексов) | На каждом деплое — runner применяет только ещё не применённые | `task db:migrate` (runner `backend/cmd/migrate`) |
| **Seeds** | Начальное наполнение справочников на пустой БД из кода | Не используются — заменены bootstrap-миграциями | — |

**Почему нет seeds в коде.** Ранее справочники (`ref_locations`, `ref_breeds`)
наполнялись через Go-пакет `pkg/seeds` при старте приложения. Это создало две
проблемы: (1) auto-seed при каждом старте — риск на каждом деплое и скрытие
ошибок; (2) дублирование источника правды между кодом и БД. Вместо этого
bootstrap-миграции применяются один раз вручную на новом окружении,
версионированы в git.

**Почему one-off через runner, а не psql руками.** Ручное применение через
GUI-клиент (Beetkeeper) не оставляет следов и про него легко забыть на prod.
Runner `backend/cmd/migrate` ведёт таблицу `applied_migrations` в самой БД:
команда `task db:migrate ENV=prod` безопасна для повторного запуска в любой
момент и применяет ровно то, что ещё не применено — забыть миграцию нельзя,
если команда есть в процессе деплоя.

## Конвенция именования

```
YYYYMMDDNNNNNN_name.sql
```

- `YYYYMMDD` — дата (год-месяц-день)
- `NNNNNN` — порядковый номер в пределах дня (6 цифр, для сортировки)
- `name` — короткое описание в snake_case

Файлы сортируются лексически — runner применяет one-off в этом порядке.
Пример: `one-off/20260728000001_regions_okato_backfill.sql`.

## Правила

1. **Idempotent.** Каждая миграция должна быть безопасна для повторного
   запуска: `ON CONFLICT DO NOTHING`, `IF NOT EXISTS`, `CASE`-обновления,
   `WHERE verified_at IS NULL` и т.п. Для one-off это страховка на случай
   первого запуска runner-а на окружении, где миграции применялись вручную.

2. **Транзакция.** Оборачивайте связанную логику в `BEGIN/COMMIT`. При ошибке
   всё откатится. Исключение — операции, которые нельзя выполнить в
   транзакции (например, `CREATE INDEX CONCURRENTLY`). Runner выполняет файл
   целиком одним Exec: без явного `BEGIN/COMMIT` PostgreSQL исполняет его как
   неявную транзакцию (всё или ничего).

3. **Порядок внутри миграции с переименованием ID** (для справочников):
   1. Вставка новых записей (`ON CONFLICT DO NOTHING`).
   2. Обновление ссылок в JSON-полях (`jsonb_agg` + `CASE`).
   3. Обновление FK-колонок.
   4. Удаление старых записей справочника (после обновления всех ссылок).

4. **Schema vs Data.** Schema-миграции (DDL) выполняются автоматически
   через `config.RunMigrations` (Ent `client.Schema.Create`) при старте
   приложения. SQL-миграции в этом каталоге — для данных (справочники) и
   для DDL, который Ent не умеет выразить (partial indexes, сложные
   ограничения и т.п.).

5. **Bootstrap vs one-off.**
   - **Bootstrap** — то, что должно существовать на любом окружении,
     включая свежее развёртывание. На существующих БД уже применён.
   - **One-off** — то, что нужно только существующим БД: на свежей БД,
     собранной Ent auto-migrate + bootstrap, он не нужен или вреден
     (например, дроп ещё не существующего индекса). Поэтому one-off не
     применяется на новом сервере, а помечается как применённый (baseline).

6. **Порядок применения на окружениях**: dev → проверка → prod. Перед prod —
   бэкап.

## Bootstrap: применение на новом сервере

Порядок развёртывания на пустой БД:

1. Запустить backend один раз — Ent auto-migrate создаст таблицы.
2. Применить справочники и пометить one-off как применённые:

```sh
task db:migrate:bootstrap            # локальная БД (ENV=local по умолчанию)
ENV=prod task db:migrate:bootstrap   # на новом сервере
```

Задача гоняет psql по всем файлам `migrations/bootstrap/*.sql`, затем
запускает `backend/cmd/migrate -baseline` — все one-off помечаются
применёнными без выполнения.

## One-off: применение на каждом деплое

Порядок важен: one-off миграции могут ссылаться на схему (колонки, индексы),
которую создаёт Ent auto-migrate при старте backend. Поэтому backend **сначала**
запускается (обновляя схему), и только потом применяются one-off:

```sh
docker compose up -d backend     # 1. Ent auto-migrate обновляет схему БД
docker compose run --rm --no-deps backend ./migrate   # 2. one-off поверх свежей схемы
docker compose up -d             # 3. остальные сервисы
```

Локально (`task db:migrate`) это неактуально — локальный backend обычно уже
запускался и схема актуальна.

```sh
task db:migrate              # локальная БД (ENV=local по умолчанию)
ENV=dev task db:migrate      # перед деплоем на dev
ENV=prod task db:migrate     # перед деплоем на prod (после бэкапа!)
```

Runner:
- создаёт таблицу `applied_migrations (name, applied_at)`, если её нет;
- сравнивает файлы `migrations/one-off/` с таблицей;
- применяет pending-файлы в порядке сортировки, каждый отмечает в таблице;
- при ошибке останавливается — оставшиеся файлы остаются pending,
  повторный запуск продолжит с места ошибки.

**Первый запуск на существующих окружениях** (dev/prod), где миграции
применялись вручную: таблицы `applied_migrations` ещё нет, поэтому runner
выполнит текущие one-off файлы повторно — это безопасно, все они idempotent,
после чего будут зафиксированы в таблице.

#### Автодеплой (GitHub Actions)

Деплой на push (`.github/workflows/deploy-dev.yml`, `deploy.yml`) применяет
one-off миграции автоматически: в backend-образ вместе с API-бинарником
собран `migrate` и SQL-файлы, а в SSH-скрипте деплоя порядок такой:

```sh
docker compose up -d backend                                # 1. Ent auto-migrate (схема)
docker compose run --rm --no-deps backend ./migrate dev     # 2. one-off (ENV=dev|prod)
docker compose up -d                                        # 3. остальные сервисы
```

Одноразовый контейнер наследует env сервиса `backend` (DB_HOST, DB_NAME и т.д.).
Если миграция падает — деплой останавливается до перезапуска остальных сервисов,
и в логах workflow видно, какой файл не применился.

> Историческая заметка: до 09.2026 миграции применялись до старта backend.
> Это работало, пока one-off не зависели от новых колонок Ent; когда появилась
> такая зависимость (`verified_at` в 3.29.0), runner падал с
> `column does not exist`. Порядок «backend → migrate → остальное» устраняет
> класс таких ошибок целиком.

На новом сервере перед первым деплоем нужно один раз выполнить bootstrap
(см. ниже) — иначе первый запуск runner-а применит все one-off на пустой БД
(сейчас они там безопасны как no-op, но полагаться на это не стоит).

#### Через psql напрямую (точечно, при отладке)

```sh
psql "$(go run ./cmd/dburl dev)" \
  -v ON_ERROR_STOP=1 \
  -f migrations/one-off/20260830000001_users_verified_at_backfill.sql
```

## Процесс для нового разработчика

1. Клонировать репозиторий.
2. Поднять локальный Postgres (см. `config.NewLocalConfig` — `localhost:5432`,
   БД `local_odnoi_krovi`, пользователь `admin`).
3. Запустить backend один раз — `task dev-backend` применит schema-migrations
   (Ent auto-migrate создаст таблицы).
4. Наполнить справочники — `task db:migrate:bootstrap` (вставит 89 регионов
   и породы; one-off пометит как применённые — на локальной БД они не нужны).
5. Можно работать.
