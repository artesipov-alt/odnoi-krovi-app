# Контекст ИИ и заметки по разработке (Backend)

Этот документ содержит критически важные знания о проекте, архитектурные решения и особенности ("подводные камни"), обнаруженные в процессе разработки. Используйте его как справочник при модификации кода.

## 1. Ent Framework и Soft Delete (Мягкое удаление)

### Архитектура Soft Delete
Мы используем механизм мягкого удаления для большинства сущностей. Реализация разделена на две части для обеспечения чистоты кода и обхода ограничений Go на циклические зависимости.

**Структура реализации:**
1.  **Поле данных (`deleted_at`)**: Определено в `backend/ent/schema/common.go` внутри `StandardMixin`. 
    *   *Важно:* Поле должно быть определено именно в пакете `schema`, чтобы Ent корректно генерировал вспомогательные методы (например, `ClearDeletedAt`, `DeletedAtNotNil`) для каждой сущности.
2.  **Логика (Хуки и Интерцепторы)**: Вынесена в отдельный пакет `backend/internal/entutil`.
    *   Это позволяет избежать циклических зависимостей (`ent` -> `schema` -> `ent`).
    *   Пакет `entutil` не импортирует сгенерированный код `ent`, а использует анонимные интерфейсы для доступа к методам мутации.

**Критическая деталь реализации (без рефлексии):**
Для доступа к методу `Client()` внутри хуков используется интерфейс с возвращаемым типом `any`, так как Go не поддерживает ковариантность типов в интерфейсах.
```go
type HasClient interface {
    Client() any
}
// Затем приведение к интерфейсу Mutator
mClient, ok := mc.Client().(Mutator)
```

### Интерцепторы vs Хуки
-   **Интерцепторы (Interceptors)**: Работают на уровне запросов (read-path). Автоматически добавляют `WHERE deleted_at IS NULL`.
-   **Хуки (Hooks)**: Работают на уровне изменений (write-path). Перехватывают `OpDelete` и превращают его в `OpUpdate` с установкой `deleted_at`.

## 2. Генерация ID
Мы используем стратегию кастомных ID:
-   **Формат**: `PREFIX-NANOHID` (например, `USR-O_o1NOQ7HZ`).
-   **Реализация**: Определена в `backend/ent/schema/common.go` с использованием `github.com/jaevor/go-nanoid`.
-   **Префиксы**: Константы (`UserPrefix`, `PetPrefix` и т.д.) заданы в `common.go`.

## 3. Паттерн Repository (Репозиторий)
Проект следует многослойной архитектуре:
-   `internal/repositories/pg`: Реализации на базе ENT.
-   `internal/services`: Бизнес-логика.
-   `internal/handlers`: HTTP-обработчики (Echo).

**Важно**: При поиске удаленных записей (например, для восстановления) необходимо использовать специальный контекст: `ctx = entutil.SkipSoftDelete(ctx)`.

## 4. Общие "подводные камни" и правила
-   **Циклические импорты**: Никогда не импортируйте пакет `ent` внутри `backend/ent/schema/...`. Вся общая логика, требующая взаимодействия с мутациями, должна быть в `internal/entutil`.
-   **Генерация методов**: Если вы перемещаете поле из миксина в миксин, обязательно проверьте, что Ent все еще генерирует методы `Clear<FieldName>` и `FieldNameNotNil`. Если методы пропали — поле должно быть объявлено явно в схеме или в миксине, который Ent считает "своим".
-   **Go Generate**: После любого изменения в `backend/ent/schema/` или `internal/entutil` ОБЯЗАТЕЛЬНО запустите:
    ```bash
    cd backend && go generate ./...
    ```
-   **Передача контекста**: Всегда пробрасывайте `context.Context`. На нем завязана логика фильтрации мягкого удаления.

## 5. Окружение и конфигурация
-   Конфигурация через `.env`.
-   БД: PostgreSQL + ENT.
-   Кэш: Redis (интерфейс в `internal/cache`).
-   Storage: S3-совместимое хранилище (VK Cloud).
