# Контекст ИИ и заметки по разработке (Backend)

Этот документ содержит критически важные знания о проекте, архитектурные решения и историю отладки ("подводные камни"), обнаруженные в процессе разработки. Используйте его как справочник.

## 1. Ent Framework и Soft Delete (Мягкое удаление)

### Финальная архитектура
Мы используем механизм мягкого удаления, разделенный на два уровня для обхода ограничений Go на циклические зависимости и обеспечения чистоты кода.

1.  **Уровень Схемы (`backend/ent/schema/common.go`)**:
    *   **Поле**: `deleted_at` (Time, optional, nillable).
    *   **Интерцептор**: Автоматически добавляет фильтр `WHERE deleted_at IS NULL` ко всем запросам на чтение.
    *   **Пропуск фильтра**: Чтобы увидеть удаленные записи (например, для восстановления), используйте `schema.SkipSoftDelete(ctx)`.

2.  **Уровень Репозитория (`backend/internal/repositories/pg/soft_delete_hook.go`)**:
    *   **Глобальный Хук**: Перехватывает операции `OpDelete` и `OpDeleteOne`.
    *   **Трансформация**: Меняет тип операции на `OpUpdate` и устанавливает поле `deleted_at`.
    *   **Регистрация**: Хук регистрируется один раз в `internal/utils/config/ent_db.go` через `client.Use(pg.SoftDeleteHook())`.

**Почему это работает:**
Использование метода `mx.SetField("deleted_at", time.Now())` внутри хука позволяет работать с любыми сущностями универсально. Это полностью устраняет проблему циклических импортов (`ent` -> `schema` -> `ent`), так как пакет репозиториев стоит "выше" сгенерированного кода и может свободно его импортировать.

## 2. История отладки и подводные камни (Post-Mortem)

В процессе поиска идеального решения мы прошли через несколько ошибок, которые важно помнить:

1.  **Циклические зависимости**: Попытка реализовать хук прямо в `ent/schema` невозможна, если хуку нужен доступ к `ent.Client`. Схема не может импортировать сгенерированный пакет `ent`.
2.  **Проблема ковариантности интерфейсов Go**: Мы пытались использовать интерфейс `Client() any`, но в Go метод, возвращающий `*ent.Client`, **не соответствует** интерфейсу, возвращающему `any`. Это заставляло нас использовать рефлексию (`reflect`).
3.  **Рефлексия vs SetField**: Мы отказались от рефлексии в пользу `SetField("deleted_at", value)`. Этот метод есть в базовом интерфейсе мутаций ENT, что позволяет писать типобезопасный код без знания конкретной сущности (User, Pet и т.д.).
4.  **Потеря хуков**: При использовании вложенных миксинов (`Mixin()` внутри `Mixin()`) генератор ENT иногда игнорирует хуки. Финальное решение с регистрацией хука в рантайме (`client.Use`) — самое надежное.

## 3. Генерация ID
Мы используем кастомные строковые ID вместо автоинкрементных чисел:
-   **Формат**: `PREFIX-NANOHID` (например, `USR-O_o1NOQ7HZ`).
-   **Реализация**: Функция `generateID` в `common.go`.
-   **Библиотека**: `github.com/jaevor/go-nanoid`.
-   **Префиксы**: Константы `UserPrefix`, `PetPrefix` и др. определены в `common.go`.

## 4. Общие правила разработки
-   **Go Generate**: После любого изменения в папке `ent/schema/` ОБЯЗАТЕЛЬНО выполните:
    ```bash
    cd backend && go generate ./...
    ```
-   **Контекст**: Всегда передавайте `context.Context` во все методы. На нем завязана логика `SkipSoftDelete`.
-   **Репозитории**: Вся работа с базой данных должна быть сосредоточена в `internal/repositories/pg`.
