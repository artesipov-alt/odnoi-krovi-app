# Контекст ИИ и заметки по разработке (Backend)

Этот документ содержит критически важные знания о проекте, архитектурные решения и особенности ("подводные камни"), обнаруженные в процессе разработки. Используйте его как справочник при модификации кода.

## 1. Ent Framework и Soft Delete (Мягкое удаление)

### Паттерн Soft Delete
Мы используем кастомный `StandardMixin` (определен в `backend/ent/schema/common.go`) для реализации механизма мягкого удаления для большинства сущностей.

**Критическая деталь реализации:**
В Ent пакеты `schema` не могут импортировать сгенерированный пакет `ent` из-за циклических зависимостей. Это усложняет реализацию хуков и интерцепторов внутри схемы.

- **Хак для доступа к клиенту:** В хуках (в `common.go`), когда нужно перенаправить операцию `Delete` на `Update` (для мягкого удаления), мы используем **рефлексию** для доступа к методу `Client()`.
- **Почему рефлексия?** Система интерфейсов Go не поддерживает ковариантность возвращаемых типов. Метод, возвращающий `*ent.Client`, НЕ удовлетворяет интерфейсу, возвращающему `any` или другой интерфейс.
- **Пример кода:**
  ```go
  // Внутри softDeleteHook в backend/ent/schema/common.go
  rv := reflect.ValueOf(m)
  method := rv.MethodByName("Client")
  if method.IsValid() {
      client := method.Call(nil)[0].Interface()
      // ... приведение к интерфейсу Mutator и вызов Mutate
  }
  ```

### Интерцепторы vs Хуки
- **Интерцепторы (Interceptors):** Используются для **чтения (read-path)**. Они автоматически добавляют условие `WHERE deleted_at IS NULL` во все запросы.
- **Хуки (Hooks):** Используются для **записи (write-path)**. Они перехватывают операции `Delete` и трансформируют их в `Update`, устанавливая метку времени в поле `deleted_at`.

## 2. Генерация ID
Мы используем стратегию кастомных ID:
- **Формат:** `PREFIX-NANOHID` (например, `USR-O_o1NOQ7HZ`).
- **Реализация:** Определена в `backend/ent/schema/common.go` с использованием библиотеки `github.com/jaevor/go-nanoid`.
- **Префиксы:** Константы (`UserPrefix`, `PetPrefix` и т.д.) заданы в `common.go`.

## 3. Паттерн Repository (Репозиторий)
Проект следует многослойной архитектуре:
- `internal/repositories/pg`: Содержит реализации доступа к данным на базе ENT.
- `internal/services`: Содержит бизнес-логику.
- `internal/handlers`: HTTP-обработчики для фреймворка Echo.

При добавлении новых методов в репозитории учитывайте, что мягко удаленные записи будут скрыты, если явно не использовать `schema.SkipSoftDelete(ctx)`.

## 4. Общие "подводные камни"
- **Циклические импорты:** Никогда не пытайтесь импортировать `github.com/artesipov-alt/odnoi-krovi-app/ent` внутри `backend/ent/schema/...`. Используйте анонимные интерфейсы или рефлексию для доступа к сгенерированным типам.
- **Передача контекста:** Всегда пробрасывайте `context.Context` через все слои. Логика мягкого удаления полагается на значения в контексте для пропуска фильтров (например, в админ-панелях или при восстановлении записей).
- **Go Generate:** После любого изменения в `backend/ent/schema/` ОБЯЗАТЕЛЬНО запустите `go generate ./...` из директории `backend`, чтобы обновить сгенерированный код.

## 5. Окружение и конфигурация
- Проект использует `.env` файлы для настройки.
- Подключения к БД управляются через `backend/internal/utils/config/ent.go`.
- Для работы с кэшем используется Redis (интерфейс в `internal/cache`).
